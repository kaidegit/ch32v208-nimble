# CH32V208 射频驱动复核（2026-10-29）

`3170f53` 修复启动和任务队列，但 GOOD/ADV 只代表控制器软件状态。
随后读取 PHY 统计发现原代码只尝试一次 TX、没有完成中断，不能据此声称已广播。
`fe6ff2e` 增加原生 macOS CoreBluetooth 扫描和 GATT 测试工具。

## 证据来源

继承的反编译注释和现有宏不作为寄存器依据。逐项复核原厂
`../wch_ble_re_artifacts/wchble_linked.elf` 的 RV32 load/store 指令及数据流。
SHA-256: `ba457f20c3ba2e95f22aeb383eefffb21c94005fbcf0ff3693b813b76a2046c6`。
表中地址是该 ELF 的函数地址，MMIO 偏移全部为字节。

| 项目 | 原错误 | 原厂指令依据 / 修正 |
| --- | --- | --- |
| BB 初始化 | 0x80000000、0x10000 | BB_DevInit 0x28a2/0x28ac: BB+0 OR 0x800000、0x10000000 |
| LLE 模式 | 写 +0x14 | RF_Tx 0x29838 写 +0x50=0x5a，RX=0x59；+0x14 初始化为0x8c |
| PHY 速率 | 1M=0，2M=0x2000 | BLE_SetPHYTxMode 0x136dc..0x13712: 1M=0x1000，2M=0 |
| RX 配置组 | 将 uint32 数组索引误作字节偏移 | BLE_SetPHYRxMode 0x137c2..0x1382c，改用核实的字节地址 |
| TX 窗口 | 固定/估算窗口，窗口归零即成功 | 1M=16*(payload+10)+316 半微秒；成功必须有 LLE bit1 |
| basic TX/RX 中断 | 将 auto sequencer 位含义套到 basic 模式 | LLE_IRQSubHandler 0x33840；basic TX=bit1，basic RX=bit0 |
| RX DMA | +0x74 指向指针变量地址 | BLE_IPCoreInit 0x13f22..0x13f2a、LLE_DevInit 0x281c4：直接数据地址，原厂 RX/TX 间隔272字节 |
| RSSI / CRC | RSSI 取 +0xc0、软件猜测 CRC | RSSI 为 BB+0x30；ble_ll_chkcrc 0x31b7c 读取 BB+0x38 bit5 |
| RF 模拟初始化 | 多处偏移和校准省略 | RFEND_DevInit/Reset/TXCtune/TXFtune/RXFilter/RXAdc，独立转录到 wch_rf_analog.c |
| 数据信道 | 所有信道按2404+2ch | ch11起需跳过广播38的2426MHz，改为2406+2ch |

追加核对：RFEND_TXCtune 0x2b23a/0x2b27e均为`andi ...,127`，GA掩码为0x7f，
CO才是0x3f。BLE_SetPHYRxMode 0x13748按`enum & 2`分出coded；enum0/1即1M/2M
共用0x08101901/0x90083/0x31624/0x28be/0x3222d0组，只改变速率选择和窗口比例。
移除误混入2M分支的coded参数。2M仍处于禁用状态，没有宣称完成2M空口验证。

校准保留实际CO/GA读数。初版额外强制VCO两个ready位，复位测试证明会停在高频点。
最终按原厂WaitTune的“两个ready位或窗口结束”退出，分别记录
`g_wch_rf_tune_ready_mask`和`g_wch_rf_tune_expired_mask`；CPU兜底超时仍失败。
BB+0x2c bits30:25 是功率枚举，并非旧注释中的晶振精度；默认使用原厂0dBm枚举9。
RXFilter 原厂是在 ready 或 LLE 窗口归零时退出并使用低5位结果，当前保留该行为，
并记录 `g_wch_rf_filter_ready` / `g_wch_rf_filter_window_expired`；初始化成功不等于
该 ready 位被观察到。加密、2M、自动应答、精确 IFS/连接时序仍未完成空口验证。

## 实机结果

1. 修正模式、PHY和模拟初始化后：1157 tick，36次真实TX完成，之后 mcause=1。
   回调指针被改成0x2b55ff01；原 RX DMA 指向全局指针变量，覆盖相邻全局区。
2. 改用独立、4字节对齐的272字节 RX 缓冲后：25009 tick，717次TX启动/完成，
   TX失败0、迟到0；716次空接收超时；host GOOD、广播使能1、异常/断言全部0。
   同时 Mac 扫描15秒收到83次回调、8个附近设备，目标0。
   这验证了稳定性和真实TX完成事件，尚不能证明空口包符合BLE。

3. 原厂 SDK Peripheral 正向对照（scratch构建，不链接到本项目）：同一板、同一Mac、
   同一探针控制下运行25秒，stage=6，GAP状态=2；15秒扫描74次目标回调，
   名称`Simple Peripheral`。因此板端和Mac扫描链路已通过空口正向对照。
4. 对比MMIO后，改用 ll_advertise_tx 0x17cb8..0x17cce 的自动BLE信道模式，
   清RFEND+0x2c bit1；移除不在BLE_RegInit流程中的额外SetSensitivity。
   自定义频率路径来自RF API，不能未经验证当作原厂BLE路径的等价替代。

5. 自动信道模式实测24993 tick时收到一份`43 0c ...` SCAN_REQ，CRC正确，
   AdvA与本机地址逐字节匹配。这是扫描器收到本机广告后发出的应答，空口TX已经成立。
   但仅9次TX后事件停住：PHY RX header flags初始化为0，漏填LL状态，
   ble_ll_rx_end因此按STANDBY处理而没有结束广告事件。
   对照上游nrf5x实现，改填`ble_ll_state_get()`；同时允许已经完成RX时调用
   `ble_phy_tx()`发送扫描响应（原代码只接受IDLE，拒绝了正常RX→TX调用）。

6. 修复接收状态后（rf-audit-5）：24995 tick，757次TX启动/完成、43次CRC正确RX。
   名称过滤为0，但复核同一CoreBluetooth UUID后有29条本板报告，manufacturer=`5743`，
   名称被macOS保留为原厂`Simple Peripheral`。这是名称缓存，不能报成“未收到广告”。
7. 硬件auto RX→TX实验（rf-audit-6）出现未完成的sequencer状态和IRQ持续重入，已撤回。
   此实验中Mac以当前名称`CH32V208-NIMBLE`明确识别本板，但连接30秒超时。
   不把该auto实现并入最终驱动，也不据此声称IFS或连接已经通过。
8. rf-audit-8：再次按名称找到设备，连接超时；CPU最终停在wait_until_start，
   SysTick=16318，TIM3.high_word=249，TX计划时间=16384152us，guard=16384052us。
   下一个TIM3周期起点恰为250*65536=16384000us；IRQ被屏蔽，UIF待处理而high_word
   不再前进，因此读时间永远跨不过guard。改为read32在IRQ锁内消费pending UIF并
   更新high_word；保留CC比较标志，ISR随后不会重复计数。
   同时收到地址匹配后关闭WFR并扩展整帧窗口，防止34字节CONNECT_IND在短WFR窗中截断。

9. TIM3修复后（rf-audit-9）：55000 tick，1664次TX启动/完成，失败/迟到/异常/
   断言均为0；95次CRC正确RX。Mac连续扫描40秒，82条目标回调，末条在扫描结束前，
   名称`CH32V208-NIMBLE`、manufacturer=`5743`。16.3秒跨周期等待故障不再复现。
   基本TX测得从命令到TX done：payload30为354us、payload23为298us，均为
   1M空口时长8*(payload+10)再加约34us（当前CPU测量，非仪器空口精度保证）。

## 早期IFS试验（后续结果见文末）

基本收发保持basic模式；原厂auto sequencer没有并入。RX结束后等待再准备TX，
该轮96MHz板的延迟校准值为112us，补上软件/RF准备和约34us硬件启动时间。
默认立即启动TX时Mac连接超时；100us试验能连接并读uptime，但随后超时；
112us试验完成了服务/特征发现、uptime读取、空echo读取、6字节写入和回读验证。
日志`probe-delay112.jsonl`最终为`exit_code=0`、`reason=probe_complete`。
这只证明当前板的实际互通，尚未通过仪器验证IFS精度、其他主频/温度或长期稳定性。
广播和扫描响应均携带完整名称，便于同MAC替换固件后刷新主动扫描缓存。

原始GDB/RAM/RTT/MMIO取证位于`/tmp/ch32-nimble-investigation/rf-audit-*`。
本地扫描JSONL位于`tools/macos-ble/.build/`（忽略，含附近设备信息）。

## 后续连接与复位复核

112us完整GATT通过一次，但重新烧录后再次出现读echo前的监督超时，不能视为可靠通过。
108us在RAM调参时连续完成6字节和64字节写入/回读。随后按原厂
LLE_IRQSubHandler 0x33902..0x339ee的{93,97,101,105,107}半微秒表，
为RX payload 0/1/2/3补偿7/5/3/1us，避免把普通包校准值直接用于空包。
后续重烧测试以默认108us及该短包补偿为准。

复位对照中，从0别名执行入口后读到PC=0、SP=0x18010000、GP=0x18000900。
物理Flash按0x08000000链接，而原入口是相对跳转，CRT在别名PC下的AUIPC计算错误。
_start现在用LUI/JALR绝对跳到canonical handle_reset，再初始化GP/SP和复制.data。
此修复同时作用于boot和完整固件；必须验证从PC0启动，不能只验证调试器设PC08000000。

静态检查现在也解码_start的LUI/JALR目标，要求绝对跳到handle_reset。
两个当前ELF通过；将入口改成相对JAL的负例被拒绝，避免后续又引入别名CRT问题。

复位后的进一步取证：canonical入口已进入wch_ble_hw_init，SP=0x20002290，
GP=0x20000900；随后高频VCO采样在3ms窗口内只见一个ready位，rf_rc断言停机。
原厂0x34086..0x3408a并不把窗口到期视为错误，之前移植额外加严了退出条件。
恢复原厂fallback并记录ready/expired掩码；初始化顺序也改为原厂的
LLE -> RFEND DevInit -> BB DevInit -> calibration。不把fallback标成全部ready。

复位独立运行final13：无GDB，10秒扫描33条目标报告；64字节写入/回读通过。
但连续测试中仍有监督超时，等待客户端主动断开完成后也未消失，因此不是已验证的
稳定连接。快照到390514 tick，3614次TX启动/完成，失败/迟到/异常/断言0，
VCO ready_mask=7、expired_mask=0。

该快照的最后一份37字节RX：end=389970540，原beg=389970222，间隔318us，
而1M整包8*(37+10)=376us。原beg实际为地址匹配捕获点，晚于包起点约58us。
改用RX完成时间减整包airtime估算preamble起点，供连接调度使用；这仍是CPU时间估计，
还未用仪器确认RX链路延迟。保留BB捕获用于关闭WFR/扩展整帧窗口和诊断。

final14的包起点修正未单独解决重连。继续对照上游PHY接口后，发现
ble_phy_rx_set_start_time只缓存时间，而LL调用者不会再调用独立ble_phy_rx；
此前WFR函数因此在调度回调发生时直接启动RX，忽略计划时间，并提前计算窗口超时。
现在RX set_start_time实际执行RX安排；WFR相对计划first-bit时间加AA捕获和裕量，
再换算剩余硬件窗口，而不是相对提前执行的IRQ回调。此接口差异会使接收窗口
在central真正发包前结束；比仅调IFS更直接地解释丢事件和监督超时。


## 最终接收调度修复实测（final15）

构建和两个ELF检查通过；probe-rs download --verify完成，随后正常reset，
未设置PC/SP、未连接GDB运行测试。连续三次独立启动macOS客户端，均在同一轮
固件运行中完成连接、服务/特征发现、uptime读取、echo读取、写入和回读校验：

| 数据 | 结果 | 总耗时（含主动断开） |
|---|---|---|
| `00..3f`，64字节 | 通过 | 0.62秒 |
| 空值，0字节 | 通过 | 1.49秒 |
| `ff0080fe7f`，5字节 | 通过 | 1.17秒 |

日志为`tools/macos-ble/.build/probe-final15-{64,empty,binary}.jsonl`，
均为`probe_complete`、`exit_code=0`、`verified=true`，且收到预期断开回调。
相比final14的连接/监督超时，修正RX实际启动及WFR时间基准后，三次完整交互
均在约1秒内完成。该结果支持接收调度错误是连接失败的关键原因。

之后GDB只读快照：24931 tick，TX启动/完成800/800，TX失败/迟到0，
RX valid115、CRC错误1，radio_state_errs/no_bufs/hw_errs均0；
异常stash及assert均0，VCO ready_mask=7、expired_mask=0。
快照保存于`/tmp/ch32-nimble-investigation/final15-snapshot.txt`。

当前响应延迟默认108us，含短包补偿；基本1M扫描、连接和GATT读写已经实机互通。
RX起点仍由CPU完成时间减airtime估算，IFS仍为本板96MHz软件调度校准值。
30分钟连接、其他主频/温度、2M、加密及仪器级时序仍未验证，不能将短测等同于
完整BLE控制器的稳定性或合规验证。

再次关闭GDB并执行正常reset：10秒主动扫描收到31条目标报告，名称为
`CH32V208-NIMBLE`；随后16字节写入/回读通过，耗时1.05秒。
日志`final15-reset-scan.jsonl`、`final15-reset-probe.jsonl`。
这次验证无需调试器修改入口或RAM参数。最后客户端正常断开，固件继续运行。
