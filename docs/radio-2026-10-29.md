# CH32V208 射频驱动复核（2026-10-29）

`3170f53` 修复启动和任务队列，但 GOOD/ADV 只代表控制器软件状态。
随后读取 PHY 统计发现原代码只尝试一次 TX、没有完成中断，不能据此声称已广播。
`fe6ff2e` 增加原生 macOS CoreBluetooth 扫描和 GATT 测试工具。

## 证据来源

继承的反编译注释和现有宏不作为寄存器依据。逐项复核原厂
`../wch_ble_re_artifacts/wchble_linked.elf` 的 RV32 load/store 指令及数据流。
SHA-256: `ba457f20c3ba2e95f22aeb383eefffb21c94005fbcf0ff3693b813b76a2046c6`。
表中地址是该 ELF 的函数地址，MMIO 偏移全部为字节。

| 项目 | 原错误 | 原厂指令依据 / 修正 |
| --- | --- | --- |
| BB 初始化 | 0x80000000、0x10000 | BB_DevInit 0x28a2/0x28ac: BB+0 OR 0x800000、0x10000000 |
| LLE 模式 | 写 +0x14 | RF_Tx 0x29838 写 +0x50=0x5a，RX=0x59；+0x14 初始化为0x8c |
| PHY 速率 | 1M=0，2M=0x2000 | BLE_SetPHYTxMode 0x136dc..0x13712: 1M=0x1000，2M=0 |
| RX 配置组 | 将 uint32 数组索引误作字节偏移 | BLE_SetPHYRxMode 0x137c2..0x1382c，改用核实的字节地址 |
| TX 窗口 | 固定/估算窗口，窗口归零即成功 | 1M=16*(payload+10)+316 半微秒；成功必须有 LLE bit1 |
| basic TX/RX 中断 | 将 auto sequencer 位含义套到 basic 模式 | LLE_IRQSubHandler 0x33840；basic TX=bit1，basic RX=bit0 |
| RX DMA | +0x74 指向指针变量地址 | BLE_IPCoreInit 0x13f22..0x13f2a、LLE_DevInit 0x281c4：直接数据地址，原厂 RX/TX 间隔272字节 |
| RSSI / CRC | RSSI 取 +0xc0、软件猜测 CRC | RSSI 为 BB+0x30；ble_ll_chkcrc 0x31b7c 读取 BB+0x38 bit5 |
| RF 模拟初始化 | 多处偏移和校准省略 | RFEND_DevInit/Reset/TXCtune/TXFtune/RXFilter/RXAdc，独立转录到 wch_rf_analog.c |
| 数据信道 | 所有信道按2404+2ch | ch11起需跳过广播38的2426MHz，改为2406+2ch |

校准保留实际 CO/GA 读数。VCO 三个采样必须同时看到 ready 位；CPU 超时失败。
BB+0x2c bits30:25 是功率枚举，并非旧注释中的晶振精度；默认使用原厂0dBm枚举9。
RXFilter 原厂是在 ready 或 LLE 窗口归零时退出并使用低5位结果，当前保留该行为，
并记录 `g_wch_rf_filter_ready` / `g_wch_rf_filter_window_expired`；初始化成功不等于
该 ready 位被观察到。加密、2M、自动应答、精确 IFS/连接时序仍未完成空口验证。

## 实机结果

1. 修正模式、PHY和模拟初始化后：1157 tick，36次真实TX完成，之后 mcause=1。
   回调指针被改成0x2b55ff01；原 RX DMA 指向全局指针变量，覆盖相邻全局区。
2. 改用独立、4字节对齐的272字节 RX 缓冲后：25009 tick，717次TX启动/完成，
   TX失败0、迟到0；716次空接收超时；host GOOD、广播使能1、异常/断言全部0。
   同时 Mac 扫描15秒收到83次回调、8个附近设备，目标0。
   这验证了稳定性和真实TX完成事件，尚不能证明空口包符合BLE。

3. 原厂 SDK Peripheral 正向对照（scratch构建，不链接到本项目）：同一板、同一Mac、
   同一探针控制下运行25秒，stage=6，GAP状态=2；15秒扫描74次目标回调，
   名称`Simple Peripheral`。因此板端和Mac扫描链路已通过空口正向对照。
4. 对比MMIO后，改用 ll_advertise_tx 0x17cb8..0x17cce 的自动BLE信道模式，
   清RFEND+0x2c bit1；移除不在BLE_RegInit流程中的额外SetSensitivity。
   自定义频率路径来自RF API，不能未经验证当作原厂BLE路径的等价替代。

5. 自动信道模式实测24993 tick时收到一份`43 0c ...` SCAN_REQ，CRC正确，
   AdvA与本机地址逐字节匹配。这是扫描器收到本机广告后发出的应答，空口TX已经成立。
   但仅9次TX后事件停住：PHY RX header flags初始化为0，漏填LL状态，
   ble_ll_rx_end因此按STANDBY处理而没有结束广告事件。
   对照上游nrf5x实现，改填`ble_ll_state_get()`；同时允许已经完成RX时调用
   `ble_phy_tx()`发送扫描响应（原代码只接受IDLE，拒绝了正常RX→TX调用）。

6. 修复接收状态后（rf-audit-5）：24995 tick，757次TX启动/完成、43次CRC正确RX。
   名称过滤为0，但复核同一CoreBluetooth UUID后有29条本板报告，manufacturer=`5743`，
   名称被macOS保留为原厂`Simple Peripheral`。这是名称缓存，不能报成“未收到广告”。
7. 硬件auto RX→TX实验（rf-audit-6）出现未完成的sequencer状态和IRQ持续重入，已撤回。
   此实验中Mac以当前名称`CH32V208-NIMBLE`明确识别本板，但连接30秒超时。
   不把该auto实现并入最终驱动，也不据此声称IFS或连接已经通过。
8. rf-audit-8：再次按名称找到设备，连接超时；CPU最终停在wait_until_start，
   SysTick=16318，TIM3.high_word=249，TX计划时间=16384152us，guard=16384052us。
   下一个TIM3周期起点恰为250*65536=16384000us；IRQ被屏蔽，UIF待处理而high_word
   不再前进，因此读时间永远跨不过guard。改为read32在IRQ锁内消费pending UIF并
   更新high_word；保留CC比较标志，ISR随后不会重复计数。
   同时收到地址匹配后关闭WFR并扩展整帧窗口，防止34字节CONNECT_IND在短WFR窗中截断。

9. TIM3修复后（rf-audit-9）：55000 tick，1664次TX启动/完成，失败/迟到/异常/
   断言均为0；95次CRC正确RX。Mac连续扫描40秒，82条目标回调，末条在扫描结束前，
   名称`CH32V208-NIMBLE`、manufacturer=`5743`。16.3秒跨周期等待故障不再复现。
   基本TX测得从命令到TX done：payload30为354us、payload23为298us，均为
   1M空口时长8*(payload+10)再加约34us（当前CPU测量，非仪器空口精度保证）。

## 当前验证边界

基本收发保持basic模式。原厂auto响应/精确IFS还未移植完成，连接/GATT不能视为通过。
广播和扫描响应均携带完整名称，便于同MAC替换固件后刷新主动扫描缓存。
