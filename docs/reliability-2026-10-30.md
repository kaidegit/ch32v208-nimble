# 2026-10-30 可靠性验证

本轮覆盖软件复位、反复连接和1M/2M持续连接读写。原始日志位于
`tools/macos-ble/.build/`，不提交附近设备信息。测试结果按每一轮实际完成情况统计，
失败不自动重试，不将恢复后的成功覆盖原失败。

## 复位故障取证与修复

增加少量校准诊断后，`reliability-cal-baseline`前8次复位通过，第9次目标消失。
自动GDB现场确认尚未进入PHY/host，assert457、analog stage3，ready_mask1：

| 高频采样诊断 | 数值 |
|---|---|
| 开始cputime | 67654us |
| 失败cputime | 107137us |
| 差值 | 39483us |
| 轮询迭代 | 2106 |
| 超时分支保存的LLE窗口 | 0 |

原顺序为“读ready -> 读硬件窗口 -> 读取CPU时间并检查10ms兜底超时”。
若执行在最后两个操作之间停顿，CPU时间已跨过兜底期限，而窗口也已正常结束，
仍会依据之前的非零窗口返回失败。以上现场直接证明，错误返回时硬件窗口已经为0；
停顿来源尚未单独确定，调试复位过程或抢占均可能产生这种读值时间差。

现先读取CPU时间，再读新的ready/窗口，优先接受硬件完成条件；时间起点也放在
装载窗口之后。RXFilter轮询有相同问题，一并调整。保留原厂ready或窗口结束的
规则，保留10msCPU兜底，不新增重试、不放宽期限、不把窗口fallback标为ready。
诊断保留三频段的起止时间、结束窗口和迭代数，便于将来区分真实硬件停顿。

基线现场：`tools/macos-ble/.build/reliability-cal-baseline/{report.json,failure.gdb.txt,failure.ram.bin}`。

## 测试方法

`tools/macos-ble/reliability.py`默认运行30次软件复位、100次重连，并分别在1M、2M
保持一个连接1800秒。复位和重连交替选择1M/2M，逐次写入并验证0/1/3/20/63/64字节。
每个持续连接阶段只有第一次连接/协商，期间不主动断开和重连。

Mac客户端持续轮换0,1,2,3,4,5,7,16,20,23,31,32,63,64字节及变化的数据；
逐轮读uptime、写echo、读回逐字节校验、确认双向PHY，并要求uptime不倒退。
读写错误、数据不符、PHY改变、意外断开或10秒无回调进展立即失败。
达到目标时长后必须再完成一整轮，输出`soak_complete`才算通过，超时退出不算通过。
轮间隔0.2秒；这不是最大吞吐测试。脚本在整个运行期间阻止Mac自动空闲睡眠。

固件运行时不连接GDB，失败后才停止并采样现场。另延长2M阶段，令同一次固件运行
跨过32位1MHz cputime计数器约71.6分钟的回卷，检查带符号时间差及定时队列边界。
软件复位不等于物理断电，未覆盖电源/温度/距离变化及多种中心设备。

完整报告记录ELF和客户端源码SHA256、Git版本及工作区变更；每次读写原始事件
保存在独立JSONL。具体命令见`tools/macos-ble/README.md`。
