## 1. 从逆向事实到实现

### 1.1 寄存器序列(BLE_SetPHYTxMode 0x135ba / BLE_SetPHYRxMode 0x13714 全量反汇编)

- **vendor phy 枚举**:0=1M、1=2M、2=coded、3=coded+bit14。逐分支核对 TX 窗口公式后确认
  **phy2 = S=8(125 kbps,64 µs/字节)、phy3 = S=2(500 kbps,16 µs/字节)**:
  两支窗口都恰为对应编码真实空口时长 +190 µs 裕量(S8:`(len+2)*64+782`,
  S2:`(len+2)*16+620`,len 为 PDU 载荷长度;另有固定项 +a4=0)。
- **BB[0x00]**:TX 位 = S8:0x2000、S2:0x2000|0x4000(bit14=S2 选择);**RX 对 S2/S8 完全相同**
  (0x2000,不清 bit14)—— 解调器从空口 CI 字段自适应编码,这是全方案的关键事实。
- **coded RX demod 组**(与 1M/2M 组不同的第二组):BB+0x10=0x34A4DF(DTM 0x3FA4DF)、
  +0x14=0x08301FF1、+0x18=0x31619、+0x20=0x90086、+0x24=0x1006310、+0x28=0x28DE。
- **TX 窗口(LLE[0x64],0.5 µs)**:S8 = `128*(len+2)+1564`,S2 = `32*(len+2)+1240`
  (即 µs = 空口时长 + 190);1M/2M 公式不变。写窗口沿用 vendor 的守护字协议
  (LLE[0x0C] bit13 保存/清零/fence/恢复 + LLE[0x08]=0x2000 预清)。
- **TX 完成后 ACK RX 窗**(rf_tx_auto_txProcess / ll_slave_process:按 `BB[0x00]>>12&3`):
  0(2M)→0x196、2(coded S2/S8)→0x43E、其余(1M)→0x1BE。
  **原“vendor给S2的窗口过短”判断撤回**：0x6000(S2)和0x2000(S8)右移12位再`&3`都等于2，
  两种编码本来就走0x43E。本移植coded总窗口同为IFS 150+393=543 µs。
- **C_PHY(coded)= 0x189(393 µs)**:ll_slave_process 锚点校正用 `widen+0x189`,
  = 同步 376 + 捕获决策延迟 ~17 µs,与 §2 的实测 18 µs 互证。
- **接收窗口预算**(地址匹配后全帧预算):vendor 公式 `win*128+868`(win=octets+4);
  本移植地址捕获重载窗口 coded 取 `(255+4)*128+868`(0.5 µs)。

## 2. S=2 首测失败与根因(值得记录的射频时序坑)

**现象**:手机上写 03(S=2)→ `phy: updated status=0 tx=3 rx=3`(LL 层切换成功),
紧接着一次 ATT Read-Blob 往返成功(coded 空口收发都通),之后连接静默 5 s →
supervision timeout(HCI 0x08)断连。写 04(S=8)则完全稳定。

**根因**:本移植从"帧完成时刻 − 按协商编码估算的空口时长"反推 `beg_cputime`
(LL 自己也按 `connsm->phy_data.rx_phy_mode` 加回帧长,两侧本来自洽)。实测表明
**该Android中心设备在观测的coded连接上仍按S=8编码发射**(本端S=2选项只约束本端TX偏好;
接收端解调自适应所以"能收到",但时间戳错):S=2 协商下每帧锚点被推晚
`ble_ll_pdu_us(len,S8)−ble_ll_pdu_us(len,S2)` = 258+48·len µs(空 PDU 258 µs),
首个 coded 事件后锚点漂移即超出窗展宽(60 µs),从此收不到中心设备 → 超时。
S=8假设与该次对端实际编码一致，故此时间戳问题未暴露。S=2/S=8不是双方必须一致的PHY协商结果。

**修复(与编码无关的时间戳)**:实测 **BB[0x38] bit6 时钟捕获 = 地址匹配事件,
每次连接 RX 都触发**(g_wch_rf_rxdiag:175/175;`捕获→RX完成` = 帧尾前
`空口载荷时长 − 18 µs`,三种帧长 12/33/36 B 的 118/286/311 µs 与公式精确吻合,
即 **捕获 ≈ 帧起始 + sync + 18 µs**;vendor coded C_PHY=376+17 同值互证)。
coded RX 改为 `beg_cputime = 捕获时刻 − ble_ll_pdu_syncword_us(mode) − 18`,
不再依赖编码假设;1M/2M 保持已验证的旧路径不动。

**残余限制**(登记,不影响本次测试):coded 协商 S=2 而 peer 实发 S=8 时,
LL 的 `ble_ll_pdu_us(len, S2)` 事件预算/`last_rxd_pdu_cputime` 仍低估
(锚点已修正,残差 ≤3.3 ms @64B,对 5 s 监督超时可忽略);coded 连接上的
DLE MaxRxTime 以 S=2 计算会高估可承载字节,大 PDU(>~64B)下事件预算可能
被低估 —— echo 测试 ≤64 B 未受影响,大流量待后续验证。

## 3. 实测结果

### 3.1 Android 手机(PEDM00,Android 14,nRF Connect,adb 驱动)

同一连接(HCI itvl=36/45 ms,timeout 5 s)依次请求,**每步均含 5 字节 echo 写读校验**:

| 选择器 | 含义 | PHY 状态读回 | echo | 结果 |
|---|---|---|---|---|
| 03 | coded S=2 | `01 03 03 00 00 03` | 64 B 逐字节一致(另测)| PASS |
| 04 | coded S=8 | `01 03 03 00 00 04` | 一致 | PASS |
| 01 | 1M | `01 01 01 00 00 01` | 一致 | PASS |
| 02 | 2M | `01 02 02 00 00 02` | 一致 | PASS |

固件日志对应 `phy: updated handle=1 status=0 tx/rx=3/3→3/3→1/1→2/2`,
全程无断连。干净断开(0x213)后广播恢复。
S=8 请求后与 S=2 请求后的 HCI 证据链见 `.build/phone-*/`(UI XML + 截图 + HCI 解码)。

### 3.2 macOS 回归(CoreBluetooth,无 PHY 请求 API,仅回归)

扫描 matched、probe(3 特征)PASS;`--phy 1m,2m` 双速率数据 PASS(修复前后各跑一遍)。

### 3.3 初版连接内请求序列(仅证明互通与HCI coded状态)

1M → S=2 → S=8 → 1M请求序列 + 每态数据校验(手机)。后续取证证明初版S2→S8

## 4. 顺带发现/登记

1. **主线固有现象(与coded无关，A/B复现；原错误码归因已撤回)**:断开(即使干净断开 0x213)后广播
   数十秒~数分钟后,偶发 `adv: complete reason=1537` → `adv: set fields failed rc=22`
   → `ble: host reset, reason=1537`→ host自动重同步、广播恢复。
   HEAD 基线(无 coded 改动)同样复现(2026-10-31 A/B,/tmp/ab-baseline.log)。
   **1537=0x601=BLE_HS_HW_ERR(1)，不是值为12的BLE_HS_ECONTROLLER。**
   原Number-of-Completed-Packets记账下溢结论没有该现场支持。PHY半包接收超时原先调用
   `ble_ll_hw_error()`，随后发送Hardware Error(1)并重置host；恢复处理见复核记录。
2. **CPU halt 伪影**:GDB halt ~9 s 恢复后,LL 停留在连接态并高频重试 TX
   (tx_fail 累积),监督超时未触发(事件调度冻结路径不检查超时)。
   仅在调试器强停时出现,真实射频丢失路径未复现;登记为已知行为。
3. S=2 请求在 Android 中心下会得到 S=8 的对端发射(§2);特征值 03/04 的读回
   (HCI coded=3)无法区分 S2/S8 —— 区分手段是本记录的吞吐/时间戳证据。
4. Mac(CoreBluetooth)没有 PHY 请求 API,coded 只能由手机验证。
