# CH32V208 NimBLE 排查记录（2026-10-29）

接手基线：`317c6ee`。以下区分 ELF/实机证据与尚未验证的推测。

## 1. 启动时 .data 已经复制错，并非运行中被未知代码清零

基线 ELF：

- `_data_lma = 0x080208cc`
- `.data` 实际 LMA `0x08021012`，VMA `0x20000000`，长度 `0x178`
- 固定地址的 `.farcode` 插在 `_data_lma` 定义和 `.data` 之间，移动了 `.data` 的实际 Flash 位置。
- GDB 实读 `0x080208cc` 起全零；运行后 `xISRStackTop` 为零，`mscratch=0xfffffe00`。

修复使用 `LOADADDR(.data)`、`ADDR(.data)`，并让装载地址按 8 字节对齐。
在 `main` 入口硬件断点处 dump RAM 的全部 376 字节 `.data`，与 ELF section
逐字节比较一致：`xISRStackTop=0x20005ab0`，`uxCriticalNesting=0xaaaaaaaa`。
CMake 还需为链接脚本设置 `LINK_DEPENDS`，否则只改 `.ld` 不会触发重新链接。

## 2. syscalls.c 的修复没有进入最终镜像

基线及只修链接脚本的 ELF，map 中 `_sbrk_r` 来自 libc，`_sbrk` 来自 libgloss。
`_sbrk` 的 `0x0801e292` 是 `ecall`；实机停在未用异常向量报告器。

原因：`port/syscalls.c` 位于 `libsegger_rtt.a`，用户静态库扫描时还没有未解决的
syscall 引用，整个 object 没被抽取；之后 newlib/libgloss 提供了默认实现。
现在将此文件直接加入两个 executable，`_sbrk`、`_sbrk_r`、malloc lock/unlock
均来自工程自身 object。因此“已经添加 _r 函数”不代表问题已经修复。

## 3. 真正的空回调/重启路径：mcause 不能检测当前是否处于 ISR

只修前两项后，实机停到 `npl_wch_eventq_get` 读取 `mcause` 后的分支：

```text
caller ra = 0x0800c8dc (ble_ll_task)
sp        = 0x20006900 (LL task stack)
pxCurrentTCB = 0x20006950
tmo       = 0xffffffff (BLE_NPL_TIME_FOREVER)
mcause    = 0x8000000e (上次 Software IRQ)
PFIC_GISR = 0x00000200 (有 pending，但没有 active ISR)
xTickCount = 1
```

`mcause` 在 `mret` 后保留上次 trap 值，原先按 bit31 判断会把任务误判为 ISR。
于是 FOREVER 的队列等待被错误替换成 `xQueueReceiveFromISR()`，空队列立即返回 NULL。
Release 的 `assert(tmo == 0)` 被 `NDEBUG` 去掉，没有拦住。

LL 紧接着执行：

```asm
lw a5, 4(a0)  # a0 == NULL，读取事件函数指针
jalr a5
```

该芯片 `0x00000004` 别名读取到向量表首项 `0x08000000`（`_start`），
因此重新执行 CRT，`ra=ble_ll_task+44` 与捕获现场一致。
**跳转目标并非总是 PC=0；不能把 alias CRT 的二次异常当成最初凶手。**

修复 NPL helpers 和上游 SCB 适配，统一读 `PFIC_GISR.GACTSTA`（bit8）。
依据：[WCH 青稞 V4 微处理器手册，PFIC_GISR](https://www.wch.cn/uploads/file/20220411/1649641123177990.pdf)。
顺带将 FromISR 的 `woken` 初始化为 `pdFALSE`，ISR 阻塞约束改用始终生效的 `configASSERT`。

## 4. 调试启动和取证代码本身的问题

- 重复设 PC / 调试器重启可保留运行中的 SysTick。startup 在 main 前打开中断时，
  tick 可以在 `pxCurrentTCB == NULL` 时进入。现在入口屏蔽 IRQ 并停 SysTick，
  由 `xPortStartFirstTask` 开中断，配置 tick 时清理 Software/SysTick pending。
- 原采样代码 `char buf[15]` 存 19 字节文本并写到索引16，越界；而三静态 TCB
  白名单也会将后来动态创建的 LL/host TCB 误报为损坏。改为每64 tick纯RAM保存PC。
- 原异常 stash 的 sp/gp/tp 写到40词数组的索引41/42/43；现放回对应 x2/x3/x4 槽。
  暂存仍会覆盖 t0/t1/t2/t3，已明确注明，不将它们当成原始寄存器。
- 原未用向量汇编桩未把 CSR 值放入 a0/a1/a2，C 报告器会用垃圾参数覆盖已保存的
  mcause/mepc/mtval。现在从已保存槽加载参数再调用。
- 删除自动改写触发器 CSR 的调用，避免覆盖 probe-rs/GDB 的硬件断点。
- 本机 probe-rs 0.32 烧录+verify 完整镜像耗时约70秒；无输出期间不要过早中止。

## 回归方式

```sh
cmake --build build -j8
scripts/check-image.py build/ch32v208_nimble.elf build/boot.elf
scripts/run.sh --verify
```

`check-image.py` 检查 ELF 的实际装载地址与 CRT symbol、字对齐、heap/stack边界，
并检查 map 中的 syscall 所属 object。基线 ELF 能稳定触发 `.data` 和 syscall
两组失败，修复镜像通过。

## 已完成的阶段验证

修复 PFIC ISR 判断后，保持 `WCH_HW_SKIP_RADIO=1` 的隔离构建运行5秒：
`xTickCount=5011`，停在 idle task，`g_exc_trap_words`、`g_stub_trap_words`、
`g_config_assert_line` 全零。此构建不再在队列空时重入 CRT。

随后恢复 `WCH_HW_SKIP_RADIO=0`；移除固定 farcode、varargs 电池、启动时自动改写
选项字节和 EHMOD 的实验路径；正常的 canary 检查改为只在异常时打印。
恢复 `ble_transport_ll_init()` 标准初始化调用，移除额外分配测试和手工 NOP 重写。

保留 RAM 飞行记录、原始异常暂存和栈边界哨兵，方便后续 RF 验证。

恢复 RF 的最终构建，实机运行至 **10000 tick**：

```text
ble_hs_sync_state = 2       # GOOD
adv_enabled = 1
ll_state = 1               # ADV
host_task_h = 0x20007690
ll_task_h = 0x20006bd0
g_config_assert_line = 0
g_exc_trap_words[0..39] = 0
g_stub_trap_words[0..7] = 0
```

RTT ring 实读包含 `hw: rf_init`、完整 `np:1..8`、GATT服务和两个特征注册，
以及 `ble: synced, own addr 50:54:7b:21:ae:eb (public)`、GAP advertise启动。
原来的1KB RTT ring在未连接读取器时会饱和并丢弃新日志，不能把日志停在某行视为CPU停机。
第二次直接重新设PC启动同样正常：2986 tick，GOOD/ADV，异常及断言全零。

构建和两个 ELF 布局检查通过；当前构建仍有上游 NimBLE 的既有编译告警
（例如被 NDEBUG 去掉的 assert 导致的 unused变量、ble_phy_mode_set声明缺失），
本轮不把“编译完成”写成“无警告”。RF空口扫描/连接/GATT收发尚未实测，
BB/LLE IRQ 仍沿用项目原来的关闭状态，本轮只确认 bring-up 和控制器广播状态。

关键 GDB 文本、RTT原始buffer和 `.data` 对比保存在 `build/investigation/`（未入库构建产物）。

第三次直接启动：3006 tick，host GOOD、广播使能/LL ADV、异常和断言全零。
依据10秒快照中TCB的 `pxStack` 与 RAM 的 A5填充估算，LL尚未使用的栈底连续区
为2296字节，host为1488字节；这些只反映当前bring-up/广播负载，不代表连接压测上限。

持续运行快照：同一次启动从3006 tick继续至 **58006 tick**，host仍为GOOD，
广播使能为1、LL为ADV，异常/断言全零。RTT heartbeat的app栈高水位为803 words。
此检查在GDB控制下运行，尚未覆盖物理断电重启和长时间空口连接压测。
